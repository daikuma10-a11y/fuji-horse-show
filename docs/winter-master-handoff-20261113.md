# 次大会へ引き継ぐ大会受付システムの仕様とWinterでの修正

2026年11月13日、主催者は今回の修正を次大会にも引き継ぎ、Autumnテストで使えた操作が開催直前に欠ける事態を防ぐよう指定した。次大会はこの修正履歴を含む共通マスターから始める。以後の修正も、対象画面、利用者から見た動作、取り込んだPR、確認できた範囲をここに追記する。

## 比較に使った保存版

- Autumnは10月7日の[受付アプリ一式](https://github.com/daikuma10-a11y/fuji-horse-show/tree/a44b46421f3d094209c61bc32d03918c9b4fff7a)。共通化時の原本比較には `841c888` と `8db7b78` の[検証記録](winter-save-validation.md)がある。古いDB導入ブランチを比較元にしない。
- Winterは11月13日の[PR #81までのアプリ](https://github.com/daikuma10-a11y/fuji-horse-show/tree/268c185d3fb7078cb548c2cea73bd4ad33e1986a)。固定Winter配備が同じコミットでREADYであることを確認した。大会本部の各タブ・受付の導線から、表示部品、データの読込・保存、帳票への接続を照合した。
- DBは読み取りで、打ち合わせ下書き・一括確定、精算専用事後登録、返金、領収書発行可能額、タイムテーブル保存、モニター配信の関数の存在を確認した。旧PR本文の「適用待ち」は当時の記録。個々の大会での実機動作は、その大会の確認記録による。

## Autumnでできて、Winterで同じ操作ができない箇所

以下は保存版の画面から確認できる差分。恒久的な削除の指示を確認できたものは含めていない。異なる点を報告するもので、この表を実装承認には使わない。

| 画面・場面 | Autumnでできたこと | Winterでの状態・現場での扱い |
|---|---|---|
| 正式出番表のモニターを出したまま本部を閉じる | 編集側の終了・応答停止で未保存プレビューを外し、正式順へ自動復帰。編集中に正式な出走組が変わった場合も古い順番を無効化 | モニターは配信済みの編集中の順を保持する。該当競技は再読込でもその順を優先する。本部を閉じる前に順を保存するか変更を取り消し、小窓で「調整中・未保存」が消えたことを確認する |
| 打ち合わせ会の外部モニター | 「打ち合わせ会用・正式反映前」を常時表示。本部からの更新が途切れた際は、最後に受けた内容を表示中と会場側にも表示 | 日別出番表と競技ごとの調整表示はある。日別表の見出しだけでは会議用か正式用かを判別できず、本部が閉じても会場側には更新停止の警告が出ない |
| モニターの文字 | 正式・打ち合わせとも、小窓または外部画面内のスライダーで文字サイズを段階調整 | 打ち合わせ会は本部の「特大」切替がある。正式出番表にはアプリ内の文字サイズ調整がない。長い名前・所属を一行に収める機能は両方にある |
| 通常受付の棄権を正式反映した後 | 受付経由で棄権した人馬も正式出番表・モニターにWDとして残る | Winterの本部正式表・モニターで末尾に残す対象は打ち合わせ会で確定した棄権・競技移動元。通常受付の棄権は申請履歴に残り、正式表の同じ末尾表示には入らない。照合時点で通常受付から反映済みで現在も棄権の該当件数は0件。事前取消・取消済み追加・精算専用の事後登録は別扱い |
| 受付の最後の一括確認 | 変更前の選手・馬の名前と、追加時の要望を送信前の一覧で再確認 | 元・先の競技と変更後の人馬は出る。変更前の人馬名、追加時の要望はこの一覧に再掲されない。個別入力時の確認と登録内容には残る |
| 本部の「申請一覧」タブ | 他のタブを開いていても、見出しの赤い数字で未反映申請の件数が分かる | 共通タブに件数を渡していない。未反映件数は「申請一覧」を開き団体別に確認する。端末から届いた要確認受付も同タブ内にある |
| 打ち合わせ会の入力・確認一覧 | 入力場所で新しい選手・馬を名簿登録。団体を開くと、その団体の保留件数と競技番号順の明細を表示 | 人馬登録には「事前登録 → 人馬の登録」を使う。全競技の確認一覧は団体別で総件数を表示するが、団体ごとの件数表示と競技番号順の並べ替えはない |
| 団体向け精算書のExcel保存 | 精算書を確認して「Excelで保存」で編集可能な .xlsx を取得 | Winterは精算書の確定前印刷・保存済み再印刷が可能。団体向け精算書自体のExcel保存の入口はない。日別出番表・成績表にはExcel保存がある |

照合時の正式モニター配信データには未保存の競技は含まれていなかった。会場の実機画面に当時何が表示されていたかは未確認。

個別の未精算明細にチェックし「入金を記録して領収書を印刷」するAutumnの一括処理は、10月の共通化で対象外と明記された。後続のPR #64でWinterに追加されたのは、確認済み入金に対する全体・選手別・馬別の領収書発行。Winterの入金記録、請求訂正、領収書発行は独立した操作である。これを当日の未修正不具合として復活させない。

## 次大会を準備するとき

1. 最新のWinter後継版を取得し、上表の修正を含む版から始める。共通の表示・操作は `components/master/` と `lib/master/` を再利用する。Winter専用ファイルに残る画面の呼び出し方、保存後の戻り先、モニター配信、印刷ボタンも引き継ぐ。部品の存在だけで画面への搭載を判断しない。
2. 大会ID、開催日・会場、打ち合わせ対象日、種目・認定順、OP資格・料金、名簿・所属、時間・会場図・帳票様式を次大会のものにする。特に、Winterの土日・競技番号・参加者・個別免除を次大会に固定しない。実データと書込先は大会ごとに分ける。
3. 大会切替で変えた箇所は、利用者が押す入口から結果まで照合する。過去に取りこぼしたのは「会議タブ→対象日→仮出番→正式一括反映」「小窓→外部表示」「事後登録→精算のみ→次の入力」「団体向け帳票→訂正後の内訳」。既存の検証結果を再利用し、未接続・意図した変更・実機未確認を区別する。
4. この比較に使った既存検査は `tests/startlist-preview.cjs`、`tests/winter-daily-monitor.cjs`、`tests/winter-meeting-startlist.cjs`、`tests/winter-meeting-positions.cjs`、`tests/winter-checkout.cjs`、`tests/winter-receipts.cjs`。6件をローカルで再実行し成功。iPad・会場モニター・プリンターの現物での通し確認とは区別する。

日別の手動スクロール、会議での担当者入力省略、精算専用の事後登録、端末の自動準備・送信、配布用の備考を空白にする方針は承認済み。旧い画面をそのまま戻さない。団体向けWeb申込一本化は大会後の別工程とする。
